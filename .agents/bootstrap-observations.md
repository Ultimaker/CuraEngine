# Custom Rule Proposals — CuraEngine

## CuraEngine disposition (reviewed against source and neighboring checkouts)

- `Cura.proto` is the authored Arcus schema; generated C++ sources are CMake
  build products (`CMakeLists.txt:35-40`). Promoted to rules 15 and 36; do not
  edit generated code. `curaengine_grpc_definitions` owns the plugin RPC
  schema in its own repository, not here.
- Strategy names alone do not imply a universal extension policy. The
  `BeadingStrategyFactory` seam is concrete; other `*Provider` and `*Adapter`
  names need call-site investigation. Promoted narrowly to rule 35.
- The detected G-code "registry" is an exporter (`src/gcode_export/`), not
  printer firmware dispatch; reject the firmware G/M-code validation and
  command-registry proposals and hooks.
- WASM is an additional Conan/CI target, not the default desktop runtime.
  Keep the native code contract and validate Emscripten when affected (rule 36).
- Package identity is in `conanfile.py`, with baseline requirements in
  `conandata.yml` and generated version from recipe metadata. Promoted to
  rule 36; consumer versions require explicit validation.
- Unit tests live in `tests/`, with integration tests under
  `tests/integration/`. Mention the appropriate test seam in a review (rule 15);
  do not require tests for every syntactic change.
- The profiler reported pytest, but `tests/runtest.py` is not a pytest suite
  and the unit-test workflow uses CTest (`.github/workflows/unit-test.yml:58`).
  The profile test commands were corrected; install a test-enabled Conan
  configuration before invoking CTest.
- Reject the proposed fixed "one file per commit", blanket PascalCase,
  and global no-rebase rules: these are statistical observations, not team
  policy. The release-tag observation is useful context but not an agent
  obligation. Do not treat the generated 400-line ratchet or complexity
  threshold as proof of existing team policy; these are new, opt-in gates.

The remaining numbered drafts below are archival evidence from the initial
profiler run. They are not instructions and may contain unresolved example
placeholders; only `.agents/rules/` is authoritative.

These are observations about how *this* repository actually works, gathered by
the agentic bootstrap. They are **not rules yet**. Each one is a signal plus the
question it raises; an agent (or a human) has to decide whether the observation
deserves to become a rule, and what the rule should actually say.

**How to act on this document**

1. Work through the proposals below, highest confidence first.
2. For each, verify the evidence yourself — the detectors are heuristics and can
   misread a repository.
3. For the ones worth keeping, write a rule file in `.agents/rules/` numbered
   a custom band: `15`–`19` (always-on), `35`–`39` (path-scoped) or `45`–`59`
   (model-decision). Managed bands (`01`–`14`, `20`–`34`, `40`–`44`) are
   regenerated by the bootstrap and hash-guarded by the rules manifest.
4. Replace every `<placeholder>` in a draft with the concrete answer for this
   repository. A rule that still contains a placeholder is worse than no rule.
5. Run `bash scripts/sync_agentic_configs.sh` so the new rule is symlinked into
   `.claude/rules/` and `.opencode/rules/`.
6. Delete or annotate proposals you reject, so the next run does not re-litigate
   a settled decision.

**The `ecosystem_contract` category is different.** Those entries describe a
surface this repository shares with something outside it — an interface
definition, a command registry, a language boundary, a published package, a
submodule graph, a deployment topology. The detector can only see that the
surface exists; it deliberately does not claim to know what the contract is.
Answering that is the charter of
`.agents/agents/ecosystem_contract_investigator/agent.md`, which appends its
findings here, and of `.agents/agents/architecture_investigator/agent.md`, which
writes the architecture section of `AGENTS.md`. Both produce proposals and prose
— neither writes into `.agents/rules/`. A contract claim about another
repository is reviewed by a human before it becomes a rule.
